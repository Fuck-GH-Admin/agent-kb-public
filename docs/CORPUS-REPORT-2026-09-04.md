# 大规模真实语料测试报告（2026-09-04）

目标：验证系统在**真实规模**（10 万级文件、GB 级文本）下的完整性与检索质量。
数据来源：4TB backup 盘（只读，全程未改动源文件），由子 agent 按"多样性优先"
策略复制 108GB 到本地 `/home/miku/Bot/kb-testdata/`（过程见该目录 STAGING-LOG.md）。

## 2. 摄取期间发现并修复的三个规模问题

| # | 问题 | 根因 | 修复 | 效果 |
|---|---|---|---|---|
| P1 | 试跑 6 分钟/119 文件，40 万文件需 333 小时 | 嵌入逐条调 API（3s/条） | **嵌入攒批**：add 期间攒 eid→text，结束时 32/批送 API，批失败逐条回退 | 14.5x |
| P2 | 批量化后仍 4m47s | 摘要逐文件调 LLM（~2.5s/文件）；中转 chat 模型忽略 system 的老问题放大 | 新增 `ingest.summarize_on_ingest` 档位：**offline**（默认，AI 编目集中给 `curate --ai`）/ ai（小批量可用） | 试跑目录 6min→**3.4s** |
| P3 | Bot 批 34 万文件进程僵死 | 代理（127.0.0.1:7890）连接半开，urlopen 120s 超时过长 | 嵌入超时 120s→**60s**；重试链已有（3 次+逐条回退） | Bot 批重启后 1h 内完成 |

运维事实（写锁的实战价值）： Downloads 批与 Bot 批并行启动，第二个被
"另一个 kb 写进程正在运行" 拒绝——并发写保护按设计工作，避免了向量竞态。

## 3. 大规模库验证结果

**完整性**：doctor 全绿（quick_check / FTS / 0 缺 blob / 0 缺源 / 维度一致）。

**性能（38.6 万条目）**：

| 操作 | 耗时 | 峰值 RSS |
|---|---|---|
| BM25+向量+rerank 检索 | 1.05–1.16s | 82–92MB |
| 语义检索（含 rerank 网络往返） | 2.83s | 740MB* |
| 批量审核 386,293 条（单事务） | 9.8s | — |

*rerank 对 50 候选逐对打分时把候选文本全部载入内存，740MB 仍远低于 3GB 红线；
如需压缩可调 `rerank.top_n`（50→20 内存约减半）。

**检索质量**：

- 两套记忆金标完全不回归（小说 1.0/1.0，kb 技术 0.67/1.0）——库扩 1 万倍，
  旧条目排名不变（过滤下推+RRF 的规模稳定性）。
- 真实语料语义命中（此前纯字面检索做不到）：
  - "怎么防止两个人同时改数据库" → `ADR-0002: 继续使用 SQLite`（sim 0.51）
  - "nginx 反向代理配置示例" → nginx conf 模板（sim 0.59）
  - "python 实现滚动数组优化动态规划" → 中文算法笔记（sim 0.57）
- 抽检暴露的真实边界：部分 PDF（学术论文）kind=pdf 但摘要稀薄——它们在
  `--review` 批量激活前未跑 `curate --ai`，属于待办而非缺陷。

## 4. 治理决策记录

系统在 **38.6 万条目 / 108GB 原始数据 / 134k 向量** 规模下：完整性无损、检索
亚秒级、内存受控、质量金标零回归、语义检索在真实杂料上有效。所有规模问题
（嵌入批量化、摘要档位、超时收紧）已修复并有 e2e/生产双重验证。
